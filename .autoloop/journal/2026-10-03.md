## 输入如何变成想法

我吸收的是“声音要可控、声音要贴着对象、状态要说清楚”的原则。铁匠铺已经有两首 BGM、人物语音和模式切换，但它们之前更像分散功能：舒缓/火炉控制灯光和语音，音乐按钮控制 BGM，访客需要自己猜两者关系。

转译成铁匠铺自己的表达，就是做“炉声火候”：不用新增播放器，也不把页面做成音频工具，只在右上角控制区下方补一条轻量状态，说明现在是炉声待点亮、舒缓听铺、静音看铺还是开炉有声。

## 创意方案竞争

方案 A：炉声火候。新颖度 4/5，它把已有声音能力组织成可理解的听觉状态；访客价值 5/5，访客能知道声音有没有点亮、点击音乐会发生什么、火炉模式是否有人物语音；场景贴合度 5/5，炉声、火候、开炉和静音都贴合铁匠铺语境；视觉影响 3/5，只新增轻量状态签，不抢 3D 主体；实现风险 2/5，只改 DOM 状态和 BGM 回执，不碰音频资源和模型。

方案 B：NPC 声源方位。新颖度 5/5，点击不同 NPC 时声音从对应空间方位传来；访客价值 4/5，沉浸感强；场景贴合度 4/5，谁说话声音从谁那里来很自然；视觉影响 2/5，默认视觉几乎无变化；实现风险 4/5，要迁移到 Web Audio 图并处理 AudioContext、自动播放和移动端差异，本轮风险偏高。

方案 C：炉前静读层。新颖度 3/5，把稳火扩展成静音加低动效的慢读状态；访客价值 4/5，适合无干扰阅读；场景贴合度 4/5，稳火收声说得通；视觉影响 2/5，默认首屏不明显；实现风险 3/5，会让稳火和音乐按钮职责混在一起。

最终选择方案 A。它不是默认选最小修补，而是承接当前作品已有的声音资产：不再往画面加东西，而是把“有没有声音、是什么火候、人物会不会开口”变成访客能读懂的现场状态。方案 B 更有野心，但今天上 Web Audio 空间化容易把本轮拖成架构重写；方案 C 会污染稳火职责。

## 今天的想法

做“炉声火候”：在右上角按钮下方新增一条状态签，随 BGM、浏览器音频解锁、静音和舒缓/火炉模式同步变化。

访客会看到什么：默认显示“炉声待点亮”，点击音乐后变成“舒缓听铺”，静音后变成“静音看铺”，切火炉后变成“开炉有声”。

访客能做什么：点音乐按钮点亮或收住声音；点舒缓/火炉按钮切换听觉和灯光火候；仍然照常拖拽看铺、切站、点人物和火炉。

访客得到什么：声音反馈不再靠猜。想安静看铺可以明确静音，想开炉听反馈也知道人物语音会加入。

## 为什么这么做

昨天做了界面减法，今天不适合再塞一排说明卡。声音状态的价值在于用很小的 UI 解决一个真实的不确定性：浏览器自动播放策略会让“代码想播放”和“访客真的听到”分离，原来的音乐按钮容易误导。

我没有做 NPC 空间音频，因为那会牵涉 Web Audio 图、AudioContext 恢复、HTMLAudioElement 改造和跨浏览器策略，风险不像一轮可回退的小锤。也没有把稳火扩展成静音模式，因为稳火已经承担减少持续动效，如果再管声音会让控制语义变浑。

本轮预期改善的是可控感和可理解性：首次访客看右上角就知道声音状态，主动点一次后能看见听觉火候变化。
